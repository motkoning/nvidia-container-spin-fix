# Review-Fix Release (v1.2.0) Implementation Plan

## Overview

Address all 8 findings from the retroactive Codex review of the shipped app (review record: `.claude/skills/codex-code-review/state/retro-review-app.review.txt`, REQUEST_CHANGES, 6 Major / 2 Minor). The safety invariants all passed review; these fixes correct real execution paths that produce false verdicts or fail for ordinary users (standard accounts, spaced paths, high-core CPUs, non-English Windows). User decisions recorded during discovery: **exit-code worker IPC** (replacing the result file), **pre-elevation consent dialog**, **conflict state = detect + guide, no auto-fix**, all 8 findings in one release.

Version: **1.2.0** (minor bump — user-visible behavior additions: consent step, new verdict states, changed error copy — while staying fully backward compatible with fixes applied by v1.1.0).

## Solution Architecture

Five design moves, applied across both surfaces (helpers stay intentionally duplicated per ARCHI.md §4):

1. **Worker IPC → enumerated exit codes** (finding 1). The worker communicates outcome solely via its process exit code; the GUI reads it from the `-PassThru` process object and maps each code to a fixed plain-English message. The result file (`$ResultFile`, `%TEMP%\NvidiaFixTool-worker-result.txt`) is removed entirely — no writable-file IPC, no cross-account path derivation, no collision/spoofing surface. Probe-verified: `$p.ExitCode` populates after `-Wait` on PS 5.1. The readout (`WaitForExit()` + `ExitCode`) sits in its own try/catch, distinct from the UAC-declined catch: `ExitCode` throws when unavailable (it is an `Int32` property, not nullable), and any readout failure maps to an honest "couldn't confirm the outcome" state — never to success, and never to "nothing was changed" (the worker may have already renamed the file). Exit-code semantics are defined by an exhaustive (state × action) matrix in Implementation Details §2.

2. **CPU measurement → locale-neutral CIM `Win32_Process` time delta** (findings 2 + 6a). **[AMENDED after code-review round 1]**: the original `Get-Process`/`TotalProcessorTime` mechanism is unusable — that property silently reads `$null` (no exception, even under `$ErrorActionPreference='Stop'`) for the SYSTEM-owned container processes when running unelevated, and `$null - $null = 0` fabricated a `Measured: 0%`. Probe-verified on this machine; the reviewer caught it (round-1 Critical). Replacement, probe-verified unelevated: snapshots of `Get-CimInstance Win32_Process -Filter "Name = 'NVDisplay.Container.exe'"`, per-PID CPU time = `KernelModeTime + UserModeTime` (100 ns units); `Δ / 10,000,000 / window-seconds / cores × 100` = % of total CPU. WMI class/property names are English-invariant, so finding 6a stays fixed; `CimCmdlets` is in-box PS 5.1. **Fabrication guard**: a `$null` `KernelModeTime`/`UserModeTime` in any snapshot maps to the **Failed** outcome — never zero-filled. Exact schedule — **GUI**: snapshots at t=0 and t=3 (one 3 s window, one delta per PID); **CLI**: snapshots at t=0, t=3, t=6 (two consecutive 3 s windows, two deltas per PID — same 6 s total as today). The verdict compares the **maximum unrounded delta** across all matched PIDs and windows against the threshold; rounding happens only in display output. Probe-verified on this machine (both instances 0.00%, agreeing with Get-Counter). No performance-counter names → works on every Windows language. The measurement function distinguishes three outcomes — **measured** (max % as above), **no process**, and **measurement failed** — and both non-measured outcomes map to *indeterminate* verdicts, never to "healthy". Timing stays within budget (GUI ~10 s expectation unchanged, ARCHI.md §19).

3. **Plugin state model gains `conflict`** (finding 7). `Get-PluginState` (GUI) and the CLI's inline checks distinguish: `nodriver` / `active` / `fixed` / `conflict` (both files present) / `missing`. Conflict behavior — per user decision, detect + guide only: diagnosis shows an orange indeterminate verdict explaining that a driver reinstall likely left a stale disabled copy next to a fresh active one; Fix and Revert **abort before any file operation** with the same explanation and a pointer to the GitHub issues page. No automatic rename/cleanup (owner-sanctioned change deferred).

4. **Explicit post-action states in the GUI** (findings 3 + 8). Two flow changes, no new widgets (existing verdict label, log box, and three buttons cover it):
   - **Consent before elevation**: clicking "Apply the fix" first shows a Yes/No `MessageBox` stating, in plain English: one NVIDIA file is renamed so it stops loading — nothing is deleted and the Undo button puts it back; the only thing lost is automatic game-profile updates between driver releases; Windows will ask for permission; a restart finishes the job. "No" logs that nothing was changed. (Copy is written in the plan's owner-gated terms above; final wording is implementer-drafted from these facts and reviewed at the code-review gate.)
   - **Post-Revert state**: after a successful Revert the handler does **not** re-run `Invoke-Diagnosis`. It sets a dedicated verdict ("Undo complete — restart your PC to finish"), keeps the log, hides Undo, and shows the action button as "Restart PC now" (existing blue reboot-pending pattern, ARCHI.md §13). "Check again" remains available and, if pressed, runs normal diagnosis (the user chose to leave the state).

5. **Mechanical correctness fixes** (findings 4, 5, 6b):
   - CLI elevation quotes `$PSCommandPath` exactly as the GUI does for its own path.
   - CLI verdict branch replaces `-lt 3` with `-lt ($oneCore * 0.7)` — one threshold everywhere (ARCHI.md §8).
   - Both scripts and README grant via SID: `icacls ... /grant '*S-1-5-32-544:F'` (probe-verified to resolve to BUILTIN\Administrators). README's manual-fix section and its Get-Counter verification snippet are updated to the locale-neutral forms in the same commit (§15 echo rule).

## Implementation Details

### 1. Fix-NvContainerSpin.ps1 (CLI)

**Current state**: 162 lines; `Measure-ContainerCpu` (55–66) uses Get-Counter; state checks inline (87–91); verdict block (109–117); self-elevation (121–125); Fix (132–154); Revert (156–161).

**Modifications**:

- `Measure-ContainerCpu` (≈55–66): rewrite to the Get-Process two-delta method. Return shape distinguishes measured / no-process / failed (e.g. a small object or sentinel convention — implementer's choice, both scripts consistent). Keep the per-sample console line ("CPU samples (% of total CPU): …") so Diagnose output stays familiar.
- State detection (≈87–91): compute `$stock` and `$off` as today, add `$conflict = ($stock -and $off)`; new state line for conflict (Yellow) before the existing three.
- Diagnosis flow (≈93–108): handle the three measurement outcomes: failed → Yellow "could not measure CPU" line, no process → existing "not running" line, measured → existing spin/no-spin lines.
- Verdict block (≈109–117): conflict → inconclusive verdict with guidance (stale leftover from driver reinstall; do not run Fix; see README/issues). Fixed-and-working branch uses `$max -lt ($oneCore * 0.7)`; any non-measured outcome keeps the existing inconclusive path.
- Self-elevation (≈121–125): quote the script path in the argument array (same treatment as `easy-tool/NvidiaFixTool.ps1:232-233`).
- Fix mode (≈132–154): before the "already fixed" check, abort on conflict with the guidance message (no file operations). `icacls` grant switches to `*S-1-5-32-544:F`.
- Revert mode (≈156–161): abort on conflict (destination exists) with the same guidance instead of letting `Rename-Item` throw.
- Comment header (≈1–36): note the locale-neutral measurement and the conflict state in one or two lines (the header must stay self-contained per §15).

### 2. easy-tool/NvidiaFixTool.ps1 (GUI + worker)

**Current state**: 288 lines; `$ResultFile` (21); `Get-PluginState` (33–39); `Get-MaxContainerCpu` (41–50); worker block (52–78) writes result file; `Invoke-Diagnosis` (163–227); `Invoke-Worker` (229–245) parses result file; Apply handler (247–267); Undo handler (269–276).

**Modifications**:

- Delete `$ResultFile` (21) and every read/write of it.
- `Get-PluginState` (33–39): check both files; return `conflict` when both exist (before the current `fixed`/`active` returns).
- `Get-MaxContainerCpu` (41–50): rewrite to the Get-Process delta method with the three-outcome return shape — same semantics as the CLI helper but the GUI schedule (snapshots at t=0 and t=3, one delta per PID; Solution Architecture §2).
- **Worker block** (52–78): replace result-file writes with enumerated exit codes. The worker determines the plugin state **first** (nodriver / active / fixed / conflict / missing — same model as `Get-PluginState`), then maps (state × requested action) via this exhaustive matrix (single source, same numbers referenced by the GUI map). Conditions are evaluated in this order so no state can satisfy two rows:

  | State \ Action | Fix | Revert |
  |---|---|---|
  | `nodriver` | `4` | `4` |
  | `conflict` (both files) | `6` — no file touched | `6` — no file touched |
  | `missing` (neither file) | `5` | `5` |
  | `fixed` (`.off` only) | `2` — already fixed | rename back → `0` |
  | `active` (stock only) | rename → `0` | `3` — nothing to undo |
  | unexpected error (any) | `1` | `1` |

  Note the deliberate fix of a naive conversion trap: the current Revert check ("no `.off` → nothing to undo", `easy-tool/NvidiaFixTool.ps1:69`) must NOT translate to code `3` directly — `missing` also has no `.off` and must yield `5`, and `conflict` must yield `6`. State detection precedes action logic. `icacls` grant switches to the SID form.
- `Invoke-Worker` (229–245): **two separate try/catch scopes with different meanings.** Scope 1 wraps `Start-Process -Verb RunAs` only — its catch is the UAC-declined path and may honestly say "Permission was declined — nothing was changed" (the worker never launched). Scope 2 wraps the post-launch readout — `$p.WaitForExit()` then `$p.ExitCode` (an `Int32` property that **throws** when unavailable rather than returning `$null`); its catch, and a defensive `$null` check, both map to the honest unknown-outcome message "couldn't confirm what happened — restart your PC, then run this tool again to check". Scope 2 must NEVER claim "nothing was changed" — the worker may already have renamed the file. Known codes map to fixed plain-English log messages. Return success only for codes 0/2/3.
- `Invoke-Diagnosis` (163–227): 
  - Measurement outcomes: no-process and failed both produce an orange indeterminate verdict ("Could not check — NVIDIA Container is not running" / "…couldn't be measured") *before* any spin branching; "healthy"/"no problem" verdicts require an actual measurement.
  - `conflict` plugin state: orange verdict + plain-English guidance (driver reinstall left a stale disabled copy; the tool won't guess — check the GitHub page); Apply and Undo hidden.
- Apply handler (247–267): insert the consent `MessageBox` (Yes/No, facts listed in Solution Architecture §4) before `Invoke-Worker 'Fix'`; "No" → log "Nothing was changed."
- Undo handler (269–276): on success, set the post-Revert state (verdict "Undo complete — restart your PC to finish", blue; action button = "Restart PC now"; Undo hidden; log preserved) instead of calling `Invoke-Diagnosis`.

## Technical Considerations

- **Pattern Usage**: verdict/state model per ARCHI.md §9 extended with one state; elevation split §12 preserved (worker IPC changes transport, not shape); color vocabulary §13 reused (orange = indeterminate/attention, blue = reboot pending); consent dialog is the only new UI element and uses stock MessageBox.
- **Safety Invariants (ARCHI.md §5)**: Diagnose paths stay strictly read-only (measurement change is read-only; conflict detection is two `Test-Path` calls). Fix/Revert file semantics are **unchanged** — same single rename, same names; conflict handling only *aborts earlier*. Consent dialog and all new user-facing copy are the owner-gated surface: the facts each message must state are pinned in this plan (approved by the user in discovery); implementer drafts wording from those facts only, and the code-review gate checks the wording against them. Nothing touches the NVIDIA service.
- **PowerShell 5.1 Compatibility**: `Get-Process`, `TotalProcessorTime`, `MessageBox`, `$p.WaitForExit()`/`.ExitCode` are all 5.1/.NET Framework stock (probe-verified on 5.1.26100). No new dependencies, no PS7 syntax.
- **Dual-Surface Sync**: the CPU-measurement helper and state detection change in **both** scripts with the same semantics; the exit-code table exists in both (worker emits, GUI maps) and must stay in lockstep — flagged for review. README echoes change in the same commit.
- **Non-Technical UX**: one added click (consent), everything else stays double-click flow; diagnosis timing unchanged (one 3 s sample); all new copy follows §15 tone rules — plain English, honest, names the next action.
- **Field Constraints (§10)**: no live plugin experiments required by any change; conflict state exists precisely because driver reinstalls happen. Fix/Revert behavioral verification on affected hardware is a release-gate note, not a plan step.
- **Edge Cases**: covered states — no driver (4), missing plugin (5), conflict (6), container not running (indeterminate), measurement failure (indeterminate), declined UAC (unchanged), null exit code (honest unknown), two GUI instances (no shared file anymore), spaced install paths (quoted), ≥64-thread CPUs (unified threshold), localized Windows (no English identifiers).

## Type Definitions
